# 정밀도 지표 일원화 및 코드리뷰 자동화 기능 개선 실행계획서

> 작성 목적: 7회차 외부 검증에서 확인된 **"정밀도 수치 4개가 SSOT 안에 상충 공존"** 문제를 구조적으로 해소하고, 동시에 지금까지 누적 검증 과정에서 드러난 **코드리뷰 자동화 도구 자체의 기능적 미비점**을 함께 정리한다. 바이브코딩(AI 에이전트 위임 개발) 특성상 항목이 누락되면 그대로 재발하므로, 본 문서는 배경·원인·조치·완료기준(DoD)을 항목별로 빠짐없이 명시한다.
> 선행 문서: `13_실운영_전환_프로덕션_준비_로드맵.md`, `15_정밀도검증_보고신뢰성_개선_실행계획서.md`, `16_RAW데이터_웹수집_실행계획서.md`

## 0. 문제 정의 — 현재 SSOT(`single_source_metrics.json`)에 공존하는 4개의 정밀도 수치

| 출처 블록 | Precision | 표본 구성 | 문제점 |
|---|---|---|---|
| `real_world_golden_set_v2_metrics` | 93.3% | raw_web_samples 60개 | Cohen's Kappa가 **정확히 1.0** — 통계적으로 비현실적, 검증자간 이견 데이터 부재 |
| `large_scale_benchmark_metrics` | 75.0% | 합성(synthetic) 210개 | 라벨 자체가 `synthetic`으로 명시돼 있어 정밀도 측정 목적엔 애초에 부적합(성능/처리량 측정용) |
| `real_world_golden_set_v3_eval` | **99.2%** | raw 34개 | 기반 데이터셋(`real_world_large_scale_dataset/`)의 **실측 라인 중 99.6%가 `// real world padding line for stress testing` 반복 텍스트** — 실제 코드 내용이 거의 없는 상태에서 측정된 값. "real_world"라는 이름과 달리 실사용 코드가 아님 |
| 커밋 메시지에만 존재(SSOT 미등록) | 79.7% | 350개 파일, TP279/FP71/FN165 | SSOT에 반영되지 않아 추적 불가, 다른 3개 수치와 조율(reconcile) 안 됨 |

**근본 원인**: (1) "정밀도"라는 단일 이름표 아래 목적이 전혀 다른 데이터셋(정확도 측정용 vs 성능/처리량 측정용)이 뒤섞여 있고, (2) "real_world"라는 라벨에 대해 실제 코드 밀도를 검증하는 절차가 없으며, (3) 여러 정밀도 수치 중 무엇이 "대표값"인지 지정하는 메커니즘이 없고, (4) 커밋 메시지 검증기(`verify_commit_message_claims.py`)가 Precision/Recall 주장은 검사 범위에 포함하지 않는다.

## 1. 설계 원칙

1. **단일 대표 정밀도(Representative Precision) 원칙**: 여러 정밀도 수치가 존재할 수 있음을 인정하되, 그중 "실사용 대표값"으로 인용 가능한 것은 **명시적 조건을 통과한 단 하나**로 제한한다.
2. **목적 분리 원칙**: 데이터셋은 반드시 `dataset_purpose`(정확도 측정용 / 성능·처리량 측정용)를 명시하고, 성능 측정용 데이터로 산출한 수치는 정밀도 대표값으로 절대 인용할 수 없다.
3. **콘텐츠 진위성 원칙**: "real_world"/"raw" 라벨을 붙이려면 실행 가능한 실제 코드 비율이 최소 기준을 넘어야 한다. 채움 텍스트(padding)로 부풀린 파일은 자동으로 재분류된다.
4. **폐기해도 삭제하지 않는다**: 대표값에서 탈락한 수치는 지우지 않고 `deprecated_metrics_archive.json`에 사유와 함께 보존한다(은폐 방지, 추후 감사 대비).
5. **커밋 메시지 검증 범위 확장**: Precision/Recall 관련 주장도 SSOT 대표값과 대조해 불일치 시 커밋을 거부한다.
6. **회귀 방지**: 이번 조치로 새로 만드는 모든 검증기는 CI 필수 게이트(merge-blocking)로 등록하고, 등록 여부를 워크플로 파일 diff로 직접 확인 가능해야 한다(과거 라운드에서 "만들고 연결 안 함"이 반복됐던 실수를 재발 방지).

## 2. 과제 A — 정밀도 SSOT 일원화 및 데이터 진위성 게이트

### A-1. 현재 4개 수치에 대한 즉시 조치

| 수치 | 조치 |
|---|---|
| 93.3% (Kappa=1.0) | **보류(HOLD)** — 이견 사례가 포함된 형태로 골든셋을 재구성하기 전까지 대표값 후보에서 제외, `deprecated_metrics_archive.json`으로 이동 |
| 75.0% (synthetic 210개) | `dataset_purpose: performance_benchmark`로 재태깅, 정밀도 대표값 후보에서 명시적으로 제외(처리 성능 지표로만 유지) |
| 99.2% (padding 데이터셋) | **즉시 폐기** — 기반 데이터셋을 A-2 진위성 검증기에 통과시켜 실패 확인 후 아카이브, "real_world" 라벨 제거 |
| 79.7% (SSOT 미등록) | SSOT에 정식 등록하되, 데이터셋 자체의 진위성(padding 비율)을 A-2로 먼저 검증한 뒤에만 후보로 인정 |

> A-1 조치 이후, 만약 4개 수치 중 대표값 조건을 만족하는 것이 하나도 없다면 **"현재 검증된 대표 정밀도 없음(INSUFFICIENT_VALID_DATA)"**을 SSOT에 명시적으로 기록한다. 억지로 아무 숫자나 대표값으로 지정하지 않는다 — 이것이 지금까지 반복된 문제의 핵심이었다.

### A-2. 콘텐츠 진위성 검증기: `scripts/validate_dataset_authenticity.py` (신규)

```
[검사 항목]
1. 실행가능 라인 비율(real_code_line_ratio) = (전체 라인 - 공백 - 순수 주석 라인) / 전체 라인
   - 임계값: real_code_line_ratio >= 0.70 이어야 "real_world"/"raw" 라벨 사용 가능
2. 반복 라인 탐지: 동일한 라인(공백 제거 후)이 파일 내 10회 이상 연속/비연속 반복 시 해당 파일을 "synthetic_stress_test"로 강제 재분류
3. 의심 키워드 탐지: "padding", "stress testing", "dummy", "placeholder", "lorem ipsum" 등이 파일 내 라인의 5% 이상에서 발견되면 자동 재분류
4. 파일명/디렉토리명에 "real_world"가 포함되어 있으나 위 1~3 기준 미충족 시 → FAIL, 라벨 사용 금지 + 자동 이름 변경 제안(예: `stress_test_dataset/`)
```

- 이 검증기는 정밀도 계산 스크립트(`18_eval_raw_web_golden_set.py`, `25_eval_real_35_samples_benchmark.py`, `27_real_scale_benchmark.py` 등) **실행 전에 선행**되어야 하며, FAIL 시 정밀도 계산 자체를 중단시킨다.
- **CI 등록 필수**: `.github/workflows/test.yml`에 이 스크립트가 실제로 호출되는지 diff로 확인할 것(§6 체크리스트 참고).

### A-3. 정밀도 보고 스키마 표준화: `precision_report_schema.json`

모든 정밀도 산출 결과는 아래 스키마를 따른다.

```json
{
  "dataset_id": "string",
  "dataset_purpose": "accuracy_measurement | performance_benchmark",
  "sample_count": "int",
  "real_code_line_ratio": "float (0~1)",
  "authenticity_check_status": "PASS | FAIL | NOT_APPLICABLE",
  "precision_percent": "float",
  "recall_percent": "float",
  "methodology": "string (측정 방법 요약)",
  "is_representative_candidate": "boolean",
  "superseded_by": "string | null",
  "computed_at": "ISO8601 timestamp"
}
```

- `is_representative_candidate = true`는 오직 `dataset_purpose == "accuracy_measurement"` AND `authenticity_check_status == "PASS"` AND `real_code_line_ratio >= 0.70`인 경우에만 자동 설정된다(사람이 임의로 true를 부여할 수 없도록 계산 스크립트 내부 로직으로 강제).
- 대표값 후보가 2개 이상이면, 표본 수가 가장 많고 이견 비율이 5~25% 범위인 것을 우선 채택하고 나머지는 `superseded_by` 필드에 채택된 항목을 명시한다.

### A-4. 커밋 메시지 검증기 확장

`scripts/verify_commit_message_claims.py`에 아래 규칙을 추가한다.

- 커밋 메시지에 `정밀도`, `Precision`, `오탐률` 등의 표현과 함께 숫자(%)가 등장하면, `single_source_metrics.json`의 **`is_representative_candidate: true`로 지정된 유일한 값**과 정확히 일치해야 한다.
- 대표값이 없는 상태(`INSUFFICIENT_VALID_DATA`)에서 정밀도를 주장하는 커밋은 **무조건 거부**한다.
- 여러 후보 수치 중 하나를 골라 유리하게 인용하는 것도 금지 — 반드시 대표값 하나만 인용 가능.

### A-5. 회귀 테스트 (필수)

- 의도적으로 padding 비율 99%인 가짜 "real_world" 데이터셋을 만들어 A-2 검증기에 투입 → FAIL 및 라벨 거부가 실제로 일어나는지 증명
- 대표값이 아닌 수치(예: 폐기된 93.3%)를 커밋 메시지에 쓰고 push 시도 → 거부되는지 증명

## 3. 과제 B — 회귀 방지 게이트 강화 (지금 당장 깨져 있는 것부터)

### B-1. 현재 실패 중인 테스트 즉시 수정
- `wincc_reviewer/tests/test_golden_set_integrity.py::TestGoldenSetIntegrity::test_valid_golden_set_v3_passes`가 현재 FAIL 상태로 확인됨(외부 검증 시점 기준). 이 테스트가 그린이 될 때까지 다른 신규 기능 작업에 착수하지 않는다.
- 원인 파악 후 "테스트를 통과시키기 위해 테스트 조건을 느슨하게 바꾸는 방식"이 아니라 **실제 골든셋 데이터를 유효한 상태로 고치는 방식**으로 해결한다(이 구분을 리뷰 시 반드시 확인).

### B-2. ruff 0건 상태를 브랜치 보호 규칙으로 강제
- 지금까지 "ruff 0건"이 여러 차례 달성됐다가 신규 코드 추가 시마다 재발했다. `--fix` 자동 적용을 pre-commit 훅에 걸고, CI의 `ruff check` 실패 시 병합이 물리적으로 불가능하도록 **GitHub 저장소의 Branch Protection Rules에서 해당 CI job을 required status check로 지정**한다(워크플로에 있는 것만으로는 부족 — 실제 병합 차단 설정까지 확인).

### B-3. 데이터셋/골든셋 변경 시 자동 재계산 + 급변 시 사람 승인
- golden set 또는 real_world 계열 데이터셋 파일이 변경되면 CI가 자동으로 정밀도를 재계산하고, 직전 대표값 대비 ±10%p 이상 변동 시 자동 병합을 금지하고 사람 승인(리뷰 approve)을 요구한다.

## 4. 과제 C — 코드리뷰 자동화 "기능" 개선 (도구 자체의 실사용성)

지금까지 6~7라운드에 걸친 검증에서 정밀도/신뢰성 문제와는 별개로 확인된, **도구 기능 자체의 실사용성 이슈**를 정리한다.

### C-1. 리포트 그룹핑/중복 압축 — Alert Fatigue 해소
- **문제(실측 확인)**: 샘플 파일 1개(`PitPumpEWSAlarm.ctl`)에서 동일 룰(`CTL_SVR_006`, 디버그 로그 패턴)이 28회 개별 항목으로 나열됨. 리뷰어가 리포트를 열자마자 피로를 느끼는 전형적 패턴.
- **개선**: 동일 `rule_id` + 동일 파일 내 반복 발생 시, 상세 위반 목록은 유지하되 리포트 상단에 **"이 파일에서 N곳에서 발견됨"** 형태의 요약 카드를 추가하고 기본적으로 접힌(collapsed) 상태로 표시한다.
- **DoD**: 동일 파일 내 동일 룰이 5회 이상 반복될 경우 자동 그룹핑되는 것을 유닛 테스트로 검증. HTML 리포트에서 실제 접기/펼치기 UI 동작 확인.

### C-2. 오탐 다발 룰 재보정 — 도메인 관용구 화이트리스트
- **문제(실측 확인)**: `CTL-AST-CFA-003`(무한루프 내 break/return 부재 → High)이 WinCC OA에서 흔한 이벤트 대기 루프(`while(true){ ...waitFor... }`) 관용구까지 일괄 탐지할 가능성 확인.
- **개선**: 도메인 전문가 검토 세션을 거쳐, dpConnect 콜백 등록·이벤트 리스너 등록 등 정상적인 무한 대기 패턴에 대한 화이트리스트 컨텍스트를 추가한다. 자동 추천(`RuleOptimizer`)은 사람이 최종 승인하는 human-in-the-loop을 유지한다(기존 방침 유지).
- **DoD**: 화이트리스트 적용 전/후로 동일 샘플셋에 대한 오탐 감소율을 측정해 `rule_fp_review_log.csv`에 기록.

### C-3. 자동화 커버리지·체커 개수의 지속 동기화
- **문제(반복 확인)**: 체커 개수가 라운드마다 33개(실측) vs 35개(주장)처럼 어긋난 사례가 있었음.
- **개선**: `verify_coverage_claim.py`의 실행 결과를 CI 빌드 아티팩트로 저장하고, README의 배지(shields.io 스타일)에 **빌드 파이프라인이 자동으로 값을 주입**하도록 한다. 사람이 README에 수치를 손으로 적는 것을 금지한다.
- **DoD**: README의 커버리지 배지 값이 CI 아티팩트 값과 항상 일치하는지 검사하는 스크립트 추가.

### C-4. 심각도별 정밀도 "분리" 노출 (도구 UI/리포트 반영)
- **문제**: 지금까지 정밀도가 전체를 뭉뚱그린 단일 숫자로만 논의돼 왔다. 실사용 리뷰어 입장에선 "Critical 룰은 믿을 만한데 Info 룰은 자주 틀린다"는 식의 세분화된 정보가 훨씬 유용하다.
- **개선**: 리포트(JSON/HTML) 및 UI에 룰별/심각도별 과거 정밀도를 함께 노출한다. 예: 위반 항목 옆에 "이 룰의 최근 30일 정밀도: 92% (참고용, N=45건 기준)" 툴팁을 추가.
- **전제조건**: 과제 A의 SSOT 일원화가 선행되어야 신뢬 가능한 수치를 노출할 수 있다(순서상 A 이후 진행).
- **DoD**: 룰 단위 정밀도 데이터가 리포트 스키마에 필드로 추가되고, HTML 리포트에서 실제로 렌더링됨을 스크린샷/스냅샷 테스트로 확인.

### C-5. 오탐 신고 → 재학습 루프의 실제 구현 확인
- **문제**: 여러 문서에서 "오탐 신고 버튼 → `FalsePositiveFilter` 재학습"이 언급됐으나, 실제 엔드투엔드로 동작하는지 이번 검증 범위에서는 확인되지 않았다.
- **개선**: (a) 리포트 UI에 오탐 신고 버튼과 API 엔드포인트, (b) 신고 데이터 저장소(테이블/파일), (c) 주기적으로 신고 데이터를 검토해 룰 임계치/화이트리스트에 반영하는 배치 작업, 이 세 가지가 실제로 연결되어 있는지 점검하고, 없다면 최소 기능(MVP)으로 구현한다.
- **DoD**: 오탐 신고 API에 실제 요청을 보내면 저장소에 기록이 남는 것을 통합 테스트로 증명.

### C-6. 벤치마크 모드와 정확도 모드의 명시적 CLI/UI 분리
- **문제**: 성능/처리량 측정용 데이터(padding 포함 대용량 파일)와 정확도 측정용 데이터가 같은 파이프라인으로 섞여 사용되면서 이번 사태(과제 A의 원인)가 발생했다.
- **개선**: CLI에 `--benchmark-mode`(성능 측정, 진위성 게이트 미적용)와 `--accuracy-mode`(정밀도 측정, `validate_dataset_authenticity.py` 게이트 강제 적용) 옵션을 명확히 분리한다. 결과 리포트 상단에도 어느 모드로 실행됐는지 배너로 표시하고, `--benchmark-mode` 결과에는 **"이 결과는 처리 성능 측정용입니다. 정밀도 대표값이 아닙니다"** 경고를 자동 삽입한다.
- **DoD**: 두 모드가 서로 다른 산출물 스키마(§2-A-3의 `dataset_purpose`)를 생성하는 것을 확인.
