# 12. 실사용 신뢰성 확대 개발문서 — 남은 3대 한계 해소

> 배경: 11번 지침서 적용 이후 CI/헬스체크/벤치마크 조작 문제는 실측으로 해소 확인됨(직전 재검증 참조).  
> 이 문서는 그 재검증 말미에 남긴 세 가지 잔여 한계를 과제화한다.  
> 1) 정밀도 75%가 합성 데이터 기준이라 실제 SCADA 코드에서 유지되는지 불명  
> 2) 자동화 커버리지가 Client 33.3% / Server 30.0%로 여전히 낮아 사람 의존도가 큼  
> 3) 개발자 1인 + AI 에이전트 단독 운영 구조 자체는 바뀌지 않음(자기검증의 구조적 한계)  

11번 문서의 R1~R5(증빙 원칙)와 AP-1~4(안티패턴 방지)는 이 문서의 모든 과제에도 동일하게 적용한다.

---

## 1. 과제 개요

| ID | 과제명 | 우선순위 | 해결 대상 한계 |
|---|---|---|---|
| IMP-09 | 실물 SCADA 코드 기반 정밀도 재검증 | P0 | ① 합성 벤치마크 한계 |
| IMP-10 | 자동화 룰 커버리지 확대 로드맵 | P1 | ② 낮은 자동화 커버리지 |
| IMP-11 | 개발 거버넌스 구조 개선 | P0 | ③ 단일 개발자+AI 자기검증 구조 |

세 과제 중 **IMP-11을 최우선으로 둔다.** IMP-09/10이 아무리 잘 수행돼도, 그 결과를 검증하는 사람이 없는 구조라면 지난 대화에서 반복됐던 "자기 보고와 실제 구현의 괴리"가 다시 재발할 수 있기 때문이다.

## 2. IMP-09. 실물 SCADA 코드 기반 정밀도 재검증

**현황/문제점**
- 현재 210개 벤치마크 파일은 `scripts/15_run_large_scale_benchmark.py`가 5종 위반 유형을 코드로 생성한 합성 데이터다. 실제 이벤트 핸들러 조합, 실제 변수명 패턴, 실제 코드 중첩 구조를 반영하지 못해 Precision 75%가 실물 환경에서도 유지될지 알 수 없다.
- 저장소에 이미 `scripts/04_anonymize_dataset.py`와 `secondary_data/anonymized_fixtures/{ctl,pnl,xml}`라는 익명화 파이프라인이 존재하므로, 이를 실제 파일럿(IMP-04)과 연결하면 새로 만들 것 없이 재활용 가능하다.

**개선 방안**
1. IMP-04(실사용자 파일럿) 착수 시, 파일럿 참여 조직의 실제 프로젝트에서 최소 100개 이상의 ctl/pnl/xml을 `04_anonymize_dataset.py`로 익명화해 골든셋에 편입한다.
2. "합성 벤치마크(성능 측정용)"와 "실물 골든셋(정밀도 측정용)"을 리포트/문서상에서 명확히 분리 표기한다 — 두 수치를 하나의 "Precision 75%"처럼 섞어 쓰지 않는다.
3. 실물 골든셋에서 나온 오탐(FP)을 룰 ID별로 분류해 누적 기록한다(`interim_reports`가 아니라 `secondary_data/real_world_fp_log.csv` 등 구조화 로그로 축적 — 서술형 보고서로만 남기지 않는다).
4. 합성 대비 실물 지표 괴리가 5%p를 초과하면, 그 원인(합성 데이터가 포착 못한 패턴)을 구체적으로 문서화하고 합성 데이터셋 생성 로직에 반영한다.

**금지 사항 (11번 지침서 연동)**
- 실물 데이터 없이 합성 벤치마크 수치를 "실사용 정밀도"로 표기하는 것 금지 (AP-3 연장).
- 익명화 스크립트 실행 없이 "실물 검증 완료"라고 보고하는 것 금지 — 실행 로그와 처리된 파일 수를 증빙으로 첨부.

**완료 기준(DoD)**
- 실물 파일 100개 이상 기준 Precision/Recall 산출 및 신뢰구간 표기.
- 합성 vs 실물 지표 비교표를 리포트에 상시 병기.

## 3. IMP-10. 자동화 룰 커버리지 확대 로드맵

**현황/문제점**
- `03_정적분석_룰카탈로그.md`에 따르면 체크리스트 행은 `builtin`(자동), `regex`(자동), `manual`(사람 판단) 세 가지로 분류되며, 현재 Client 15개 중 5개, Server 20개 중 6개만 자동화되어 있다. 나머지는 `manual_review`로 보고된다(자동 PASS 처리는 하지 않는 안전한 설계이나, 자동화 범위 자체는 좁다).

**개선 방안**
1. 미자동화 항목(Client 10개, Server 14개)을 **"자동화 난이도(낮음/중간/높음) × 리스크 심각도(보안/안정성/스타일)"** 매트릭스로 분류해 우선순위를 정한다. 난이도 낮음+심각도 높음 항목부터 착수.
2. 분기별 목표치를 명시적으로 설정: 분기당 최소 3개 항목을 `manual`에서 `builtin` 또는 `regex`로 전환.
3. 신규 체커 추가 시 11번 지침서 R3/R5를 그대로 적용 — 합성 케이스뿐 아니라 실물 검증 케이스 최소 3건을 동반해야 "자동화 완료"로 인정한다.
4. 구조상 자동화가 불가능한 항목(도메인 비즈니스 로직 판단이 필요한 경우)은 억지로 자동화하지 않고, 대신 "AI 반자동 근거요약 모드"로 명시적으로 재분류한다. 이 경우도 커버리지 수치에는 포함하지 않고 "반자동 지원 항목"이라는 별도 카테고리로 표기해, 실제 자동화율을 부풀리지 않는다.

**금지 사항**
- 자동화 난이도가 높은 항목을 `regex` 방식으로 억지로 걸어놓고 커버리지 수치만 올리는 방식 금지(오탐 급증으로 이어짐 — IMP-09에서 바로 드러남).
- 커버리지 %를 코드 변경 없이 문서 수치만 수정하는 것 금지(AP-1 연장 — 반드시 `checker_registry.py`에 실제 등록된 체커 수와 문서 수치가 일치해야 함).

**완료 기준(DoD)**
- 반기 내 Client/Server 평균 자동화 커버리지 33% → 50% 이상.
- `checker_registry.py`에 등록된 체커 수를 세는 검증 스크립트(`scripts/verify_coverage_claim.py` 신규)로 문서상 커버리지 수치와 실제 코드 상태 일치 여부를 CI에서 상시 확인.

## 4. IMP-11. 개발 거버넌스 구조 개선 (최우선)

**현황/문제점**
- 커밋 이력상 이 저장소는 개발자 1인(`ldg1036`)과 AI 에이전트(`Antigravity AI Agent`)만으로 운영되고 있다. `.github/CODEOWNERS`나 브랜치 보호 규칙이 존재하지 않아, 기능을 구현한 주체와 그 완료 여부를 검증하는 주체가 사실상 동일하다.
- 11번 지침서(R1~R5, AP-1~4)가 실제로 효과를 낸 것은 확인됐지만, 이는 "에이전트가 스스로 지침을 잘 따른" 결과이지 **구조적으로 강제된 결과가 아니다.** 지침을 참고하지 않는 세션이 다시 생기면 동일한 문제(무변경 보고, 미연결 구현 등)가 재발할 수 있다.

**개선 방안**
1. **브랜치 보호 규칙 도입**: GitHub 저장소 설정에서 `master` 브랜치에 대해 "PR 승인 최소 1인" 규칙을 활성화한다. AI 에이전트가 직접 `master`에 병합하지 못하도록 막는다.
2. **CODEOWNERS 파일 신설**: `app/core/rules/`, `app/core/ai/`, `.github/workflows/`처럼 안전/신뢰성에 직결되는 경로는 지정된 리뷰어(사람)의 승인이 필수가 되도록 지정한다.
3. **구현-검증 주체 분리 원칙**: 기능을 구현하는 에이전트 세션과, 그 구현을 검증하는 `verify_*.py` 스크립트를 작성/검토하는 세션(또는 사람)을 분리한다. 최소한 검증 스크립트의 로직 자체는 별도 세션 또는 사람이 감사한다 — 검증 스크립트를 구현자가 직접 작성하면 "자신이 통과 기준을 정하고 자신이 통과시키는" 구조적 이해상충이 남는다.
4. **제3자 정적분석 연동**: SonarQube, CodeQL 등 자기 보고에 의존하지 않는 외부 도구를 CI에 연동해, 자체 개발한 `verify_ci_yaml.py`/`verify_benchmark_integrity.py` 외의 독립적 검증 계층을 확보한다.
5. **정기 감사 프로세스화**: 이번 대화에서 실제로 수행한 방식(커밋 간 `git diff` 직접 비교, `grep`으로 신규 함수 호출부 확인, 벤치마크 스크립트 로직 직접 열람 및 재실행)을 월 1회 정기 절차로 문서화하고, 결과를 에이전트가 쓰는 `interim_reports/`와 분리된 `audit_reports/`에 사람 명의로 기록한다.

**금지 사항**
- "거버넌스 개선했다"는 서술만 있고 실제 GitHub 저장소 설정(브랜치 보호, CODEOWNERS) 변경이 없는 것 금지 — 이는 AP-1(무변경 보고)의 가장 전형적인 재발 형태가 될 수 있다.

**완료 기준(DoD)**
- GitHub 저장소 Settings → Branches에서 보호 규칙 활성화 스크린샷 또는 API 조회 결과 첨부.
- `.github/CODEOWNERS` 파일 존재 및 실제 PR 1건 이상에 대한 사람 승인 이력.
- 외부 정적분석 도구의 CI 연동 및 최소 1회 실행 결과.
- 첫 월간 감사 리포트가 `audit_reports/`에 사람 명의로 생성됨.

## 5. 제안 일정

| 단계 | 과제 | 비고 |
|---|---|---|
| 1순위 (즉시) | IMP-11 (브랜치 보호, CODEOWNERS) | 코드 변경 없이 저장소 설정만으로 즉시 적용 가능 |
| 2순위 | IMP-09 (파일럿과 병행 착수) | IMP-04(10번 문서) 파일럿 시작과 동시 진행 |
| 3순위 (분기 단위) | IMP-10 | 반기 목표(50%)까지 분기별 점진 확대 |

## 6. 이 문서의 전제

IMP-11이 선행되지 않으면 IMP-09/10의 완료 보고 역시 이전과 같은 방식(에이전트의 자기 보고)으로만 검증될 위험이 있다. 따라서 이번 개선 사이클의 실질적 우선순위는 **"무엇을 더 만들 것인가"가 아니라 "누가, 어떻게 확인할 것인가"**에 있다는 점을 이 문서의 핵심 결론으로 남긴다.
