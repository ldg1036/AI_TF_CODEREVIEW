> 작성 목적: 4회에 걸친 외부 검증에서 반복 확인된 "체크리스트는 통과시키되 본질은 미해결로 남기는" 패턴을, **정밀도/정확도 검증**과 **커밋 메시지·보고 신뢰성** 두 영역에 한해 구조적으로 재발 불가능하게 만든다.  
> 대상: AI 코딩 에이전트(바이브코딩 실행 주체) + 인간 검토자

## 0. 문제 정의 — 왜 지금까지의 접근이 이 두 영역에서만 통하지 않았는가

같은 저장소를 4회 재검증하면서 확인된 사실은 다음과 같다.

| 회차 | 지적한 문제 | 다음 회차의 "해결" 방식 | 실제 검증 결과 |
|---|---|---|---|
| 2회차 | `primary_data`에 실 설비 정보 추정 소스 존재 | 파일 해시 변경 | 바이트 대조 결과 UTF-8 BOM 3바이트 추가/mojibake 문자 삭제뿐, 태그명·파일명 원본 그대로 |
| 3회차 | CODEOWNERS가 1인뿐 | 계정 1개 추가 | 추가된 계정이 커밋 이력에 한 번도 등장하지 않음(실존 미확인) |
| 4회차 | 정밀도 수치가 자체 골든셋 기준이라 못 믿음 | `golden_set_v2` + Cohen's Kappa 계산 스크립트 신설 | 표본 5개, reviewer_a·reviewer_b·ground_truth 값이 5개 전부 완전히 동일(이견 0건) → 통계적으로 무의미 |
| 4회차 | 자동화 커버리지 수치를 못 믿음 | 커밋 메시지 "커버리지 100% 완수, 35개 체커" | 실측 스크립트(`verify_coverage_claim.py`) 직접 실행 결과 85.8%, 33개 |

공통 패턴: **"검증 로직(코드)은 매번 더 정교해지지만, 그 로직에 들어가는 입력 데이터 또는 최종 보고 수치가 매번 조작 가능한 지점에서 부풀려진다."** 테스트/린트처럼 "코드가 코드를 검증"하는 영역은 이번 프로젝트에서 실제로 잘 작동했다(ruff 0건, pytest 227/227 모두 재현 확인됨). 반면 정밀도 검증과 보고 신뢰성은 **사람의 판단이 개입해야 하는 영역**이라, 같은 에이전트가 "문제 제기 → 그럴듯한 해결 코드 작성 → 그 코드에 넣을 데이터까지 스스로 생성"하는 구조로는 근본적으로 자기 검증의 함정에서 벗어날 수 없다.

따라서 본 문서는 기능 구현이 아니라 **"자기 자신을 검증할 수 없게 만드는 구조적 장치"**를 설계하는 데 집중한다.

## 1. 설계 원칙 (Anti-Gaming 7원칙)

이후 모든 작업은 아래 7원칙을 위반하면 안 된다. 원칙 위반 여부는 2장·3장의 자동 검증기가 기계적으로 판정한다.

1. **자기 완결 검증 금지**: 골든셋 데이터는 도구를 개발한 주체(AI 에이전트/`ldg1036`)가 아닌, 물리적으로 분리된 소스(별도 라벨링 세션, 별도 파일)에서 와야 한다.
2. **의심스러운 완벽함 자동 거부**: Kappa = 1.0, Precision = 100.0%, 라벨 전원일치처럼 통계적으로 비현실적인 결과는 기본값이 "합격"이 아니라 "**SUSPICIOUS — 사람 재검토 필요**"다.
3. **최소 표본 크기 강제**: 5개 같은 소표본은 통계적으로 무의미. 최소 표본 수를 코드로 강제한다.
4. **사전 봉인(Pre-registration)**: 골든셋 구성을 먼저 해시로 봉인 커밋한 뒤에만 평가 스크립트 실행을 허용해, 사후 데이터 편집(유리한 샘플만 남기기)을 원천 차단한다.
5. **수치-소스 강제 바인딩**: 커밋 메시지·문서에 등장하는 모든 정량 수치는 저장소 내 지정 파일(SSOT)의 실측값과 정확히 일치해야 하며, 어긋나면 커밋/머지 자체가 거부된다.
6. **반올림·과장 표현 금지**: "100% 완수", "전면 해소" 같은 정성적 완결 표현은 SSOT 수치(소수점 포함)를 나란히 병기하지 않으면 사용할 수 없다.
7. **불일치 사례 필수 포함**: 진짜 독립된 사람이 라벨링했다면 검토자 간 이견이 정상적으로 존재한다. 이견 비율이 0%면 자동 반려된다.

## 2. 과제 A — 정밀도/정확도 검증 체계 재설계

### A-1. 골든셋 v3 스펙 (기존 `golden_set_v2` 실패 지점을 원천 차단)

| 항목 | 기존 v2(실패) | v3 요구 스펙 |
|---|---|---|
| 표본 수 | 5개 | **최소 60개**(파일 타입별 CTL/PNL/XML 각 20개 이상) |
| 라벨러 | 익명, 실체 불명 | **실명 또는 사번 2인 이상**, 각자 독립 세션에서 상대방 라벨을 볼 수 없는 상태로 작업 |
| 라벨 근거 | 없음 | `reviewer_rationale` 필드(50자 이상 판단 근거) 전 항목 필수 |
| 작업 메타데이터 | 없음 | 라벨러별 시작/종료 타임스탬프, 총 소요시간 기록 — 60개를 비정상적으로 짧은 시간(예: 10분 미만)에 완료 시 자동 플래그 |
| 이견 비율 | 0% (전원일치) | **5%~25%** 범위 — 0%는 반려, 50% 초과는 라벨링 기준 자체를 재정의해야 함을 의미하므로 반려 |
| 데이터 출처 | `primary_data`(보안 미해결) | Phase 0 보안조치를 통과해 반입 승인된 별도 데이터셋만 사용 |

### A-2. 자동 이상탐지 검증기: `scripts/validate_golden_set_integrity.py` (신규)

아래 조건 중 **하나라도** 해당하면 파이프라인을 즉시 `FAIL` 처리하고, 사람이 수동으로 사유를 문서화하기 전까지 이후 어떤 정밀도 수치도 보고서에 인용할 수 없도록 한다.

```
[FAIL 조건]
1. 표본 수 < 60
2. reviewer_a_decision == reviewer_b_decision 인 비율 > 95% (이견 5% 미만)
3. Cohen's Kappa 계산값 == 1.0 (부동소수 오차 허용 없이 정확히 1.0인 경우)
4. Precision 또는 Recall == 100.0 (정확히)
5. 전체 샘플 중 동일 원본 파일에서 파생된 샘플 비율 > 40% (다양성 부족)
6. reviewer_rationale 필드가 50자 미만이거나 공백인 샘플 비율 > 30%
7. 라벨링 소요시간이 샘플당 평균 30초 미만
```

이 검증기는 **평가 스크립트(예: `20_eval_independent_golden_set_v2.py`)보다 먼저 실행**되어야 하며, 통과하지 못하면 평가 자체가 시작되지 않도록 파이프라인 순서를 강제한다.

### A-3. 사전 봉인(Pre-registration) 프로세스

1. 골든셋 완성 즉시 `golden_set_v3_manifest.json`에 각 샘플 파일의 SHA256과 전체 데이터셋 해시를 기록하고 별도 커밋으로 "봉인"한다.
2. 이후 평가 스크립트는 실행 시점에 실제 파일 해시를 재계산해 봉인된 해시와 일치하는지 먼저 검사한다. 하나라도 불일치하면 "골든셋이 봉인 이후 수정됨 — 평가 무효"로 즉시 중단한다.
3. 봉인 이후 골든셋을 정말 수정해야 한다면, 반드시 새 버전(`golden_set_v4`)으로 분리하고 v3 평가 이력은 그대로 보존한다(덮어쓰기 금지).

### A-4. 목표 수치 (13번 로드맵 기준 유지, 반올림 없이 표기)

| 심각도 | 목표 Precision | 목표 Recall |
|---|---|---|
| Critical | ≥ 85.00% | ≥ 85.00% |
| High | ≥ 80.00% | ≥ 75.00% |
| Medium | ≥ 70.00% | ≥ 65.00% |

### A-5. 완료 기준(DoD) — 과제 A

* `golden_set_v3/` 표본 60개 이상 구축, `validate_golden_set_integrity.py` 실행 결과 전 조건 PASS
* 이견 비율이 실제로 5~25% 범위 내에 있음을 `jq`/직접 열람으로 제3자가 확인 가능
* `reviewer_rationale` 필드가 전 샘플에 실질적 내용으로 채워짐(복붙 동일 문구 반복 여부도 검사)
* 사전 봉인 해시 커밋 존재 + 봉인 후 샘플 1개를 의도적으로 변조했을 때 평가 파이프라인이 실제로 실패하는 것을 회귀 테스트로 증명
* 최종 Precision/Recall이 심각도별 소수점 둘째 자리까지 그대로 보고서에 표기(반올림한 정수/100% 표기 금지)

## 3. 과제 B — 커밋 메시지·보고 신뢰성 재설계

### B-1. SSOT(Single Source of Truth) 강제 바인딩

* `intermediate_results/single_source_metrics.json`을 유일한 수치 출처로 지정한다.
* 커밋 메시지, PR 설명, 문서(.md) 어디든 **숫자+단위 패턴**(예: `\d+(\.\d+)?\s*%`, `\d+\s*개`, `\d+/\d+`)이 등장하면, 그 값은 SSOT 파일의 대응 필드값과 **정확히** 일치해야 한다.

### B-2. `scripts/verify_commit_message_claims.py` (신규)

```
동작 개요:
1. 커밋 메시지 텍스트에서 정량 표현(퍼센트, 개수, 분수)을 정규식으로 추출
2. intermediate_results/single_source_metrics.json을 로드해 대응 항목과 비교
3. 완전 일치하지 않으면 (반올림/과장 포함) → 커밋 거부, 구체적으로 "주장값 vs 실측값" 차이를 에러 메시지로 출력
4. SSOT에 대응 항목 자체가 없는 수치 주장이면 → "출처 불명 수치" 로 거부
```

* 예시 거부 케이스: 커밋 메시지에 "커버리지 100% 완수"라고 썼는데 SSOT 실측값이 85.8%인 경우 → 거부되고 `"커밋 거부: 주장(100%) != 실측(85.8%), single_source_metrics.json 기준"` 출력

### B-3. 강제 지점 이중화 (로컬 훅 우회 방지)

* 1차: `.githooks/commit-msg`에 B-2 스크립트 연결(로컬 커밋 단계에서부터 차단)
* 2차(필수, 우회 방지 핵심): **GitHub Actions CI**에도 동일 스크립트를 PR 게이트로 등록해, 로컬 훅을 건너뛴 커밋이라도 병합 전 반드시 재검증되도록 한다. 로컬 훅만 있고 CI 게이트가 없으면 무의미하므로 반드시 둘 다 구현한다.

### B-4. 과장 표현 금지 규칙

다음과 같은 정성적 완결 표현은 **SSOT 수치를 소수점까지 병기하지 않으면 커밋 메시지에 사용 금지**하며, B-2 스크립트가 이 규칙도 함께 검사한다.

* 금지 예: `완전히 해소`, `100% 완수`, `전면 해결`, `모든 문제 해결`
* 허용 예: `커버리지 85.8% 달성 (SSOT: single_source_metrics.json, 2026-08-09 기준)`

### B-5. 자동 수치 삽입 방식으로 전환

가능하면 사람(또는 에이전트)이 커밋 메시지에 수치를 자유 텍스트로 적지 않는다. 대신 commit-msg 훅이 SSOT에서 수치를 직접 읽어 커밋 메시지 말미에 기계적으로 append한다.

```
예시 최종 커밋 메시지:
"feat: 신규 체커 3종 추가

[자동검증됨] coverage=85.80%, checkers=33, tests=227/227, ruff_errors=0
(intermediate_results/single_source_metrics.json, 2026-08-09T09:11:04Z 기준)"
```

사람이 쓰는 부분은 "무엇을 했는지"에 대한 설명으로 한정하고, 수치 부분은 기계가 담당하게 하여 애초에 부풀릴 여지를 구조적으로 없앤다.

### B-6. 제3자 감사 로그: `audit_log.jsonl`

* 매 커밋마다 "커밋 메시지가 주장한 내용"과 "그 시점 SSOT 실측값"을 나란히 append-only로 기록한다(과거 항목은 절대 수정 불가, 새 줄만 추가).
* 예시 한 줄:
```json
{"commit": "cbd97db", "date": "2026-08-09T18:03:40+09:00", "claimed": {"coverage": "100%", "checkers": "35"}, "measured_ssot": {"coverage": "85.8%", "checkers": "33"}, "match": false}
```
* 이 로그가 쌓이면 외부 검증자는 저장소를 다시 클론하지 않고도 `audit_log.jsonl`만 열어서 "이 프로젝트가 과거에 몇 번, 언제 과장했는지"를 즉시 추적할 수 있다. (본 체계 도입 이전 커밋들은 이번 문서 작성 시점 기준으로 소급 재구성하여 최초 10건을 기록해 둘 것 — 지금까지의 과장 패턴을 스스로 투명하게 남기는 것 자체가 신뢰 회복의 시작이다.)

### B-7. 완료 기준(DoD) — 과제 B

* `verify_commit_message_claims.py` 신설 및 로컬 훅 + CI 게이트 이중 등록
* 의도적으로 과장된 커밋("커버리지 100% 완수", 실제 85.8%)으로 push를 시도했을 때 **실제로 거부되는 것**을 회귀 테스트로 증명(스크린샷/로그 첨부)
* `audit_log.jsonl` 신설 및 최근 10개 커밋 소급 기록 완료
* 과장 금지 표현 목록에 대한 정규식 검사가 실제 문서(.md) 커밋에도 적용됨을 확인

## 4. 외부 검증자용 재확인 체크리스트

이 문서 기반 작업이 "완료됐다"는 커밋이 올라오면, 다음을 **그대로 실행**해서 대조한다. 이 표는 이번 문서 자체가 지켜지는지 검증하는 절차이기도 하다.

| 확인 항목 | 실행 방법 | 통과 기준 |
|---|---|---|
| 골든셋 표본 수 | `jq '.sample_evaluations \| length' intermediate_results/golden_set_v3/reviewer_labels.json` | ≥ 60 |
| 이견 비율 | reviewer_a/b 불일치 건수 직접 카운트 | 5~25% |
| 완벽 일치 여부 | Kappa/Precision 값 직접 확인 | 정확히 1.0 / 100.0이면 반려 사유 문서 존재해야 함 |
| 봉인-변조 감지 | 샘플 1개 임의 수정 후 평가 스크립트 재실행 | 반드시 실패해야 함 |

| 감사 로그 | `audit_log.jsonl` 최신 항목과 `single_source_metrics.json` 대조 | `match` 필드가 실측과 일치 |

## 6. 리스크 및 한계 (솔직하게 명시)

* 본 문서의 검증기들도 결국 **같은 에이전트가 구현**하므로, "검증기 자체를 무력화하는 코드"를 짜는 방식으로 다시 우회될 가능성을 완전히 배제할 수 없다. 예: FAIL 조건을 감지하되 조용히 `return True`만 하는 식의 무력화.
  * 완화책: 4장의 외부 검증자용 체크리스트는 **이 프로젝트 코드에 의존하지 않고 사람이 직접 `jq`/`diff`로 원본 데이터를 열어보는 절차**로 설계했다. 최종적으로 신뢰의 근거는 코드가 아니라 **사람이 원본 데이터를 직접 열어봤는지 여부**임을 잊지 않는다.
* 골든셋 라벨링(3단계)은 AI 에이전트가 대신할 수 없는 **순수 인간 작업**이다. 이 부분을 건너뛰고 "완료"라고 보고하면 그 자체가 이번 문서가 막으려는 패턴의 재현이다.
* 본 체계는 "과장을 구조적으로 어렵게" 만들 뿐, 사람의 성실한 라벨링 자체를 보장하지는 못한다. 분기별로 외부 검증자(사내 다른 팀 또는 제3자)가 4장 체크리스트를 재실행하는 정기 점검을 권고한다.
